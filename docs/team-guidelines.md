# 115-1 軟體工程學期專案｜團隊開發規範

本文件記錄空間查詢、預約借用、志願排課的分工與業務規則。技術選型、共用認證、樣板目錄與 migration 序號依[純 Python 全端重構協作契約](refactor-contracts.md)。

## 1. 系統範圍與主責

各組員負責自己模組的 FastAPI 路由與 Jinja2 頁面，共用 PostgreSQL。Uvicorn 啟動同一個網站與 API 服務。

| 主責 | 課程要求與分工 | 其他組員怎麼接 |
| --- | --- | --- |
| 空間查詢組員（兼共用帳號） | 提供註冊、老師帳號審核、登入、登出。學生註冊後立即啟用，老師須由管理員核准後才能登入。訪客可查教室、看樓層位置及 360° 全景；管理員可新增、修改、刪除教室。 | 提供目前登入者、角色及共用教室清單。借用與排課組員用固定的使用者、教室編號建立紀錄。 |
| 借用組員 | 登入後以週查看教室借用狀況；申請教室與多項物品；管理員核准或退件、填審核意見、登記借出與歸還，並提供歷史紀錄。 | 讓排課模組能查到已核准的借用與受影響的申請，讓週檢視也能讀到正式課表。 |
| 排課組員 | 老師可增刪改查自己的課程、時段與希望教室；管理員可指派老師、維護所有課程、看週曆與衝突清單，並拖曳調整時段。 | 提供正式課表與調課申請；涉及已核准借用時通知管理員協調。 |

## 2. 專案目錄與檔案用途

各模組依[重構協作契約](refactor-contracts.md)的目錄分工。例如借用頁面放在 `templates/bookings/`，路由放在 `api/app/routers/bookings.py`。資料表變更放在 `database/migrations/`；若影響週課表，請排課組員一起核對。

## 3. 頁面、API 與登入

頁面繼承 `templates/base.html`。訪客可查教室；需登入的操作由後端檢查使用者身分，管理員專用操作另驗證管理員角色。瀏覽器 Cookie 與 API Bearer 憑證的讀取順序依重構協作契約。各模組共用教室的 `room_id` 與使用者的 `user_id`。

未登入回傳 HTTP 401，權限不足回傳 403，時段衝突回傳 409。頁面顯示相應提示；核准時重新檢查時段占用。

## 4. 資料庫欄位與版本如何同步

**一份資料由一個模組維護，其他模組以編號引用。** 下表是三人開工前應核對的最小共用欄位。定稿時要補齊型別、必填與否、預設值、唯一限制及外鍵，尤其是會被其他模組讀取的欄位。

| 資料 | 建議欄位或關聯 | 維護規則 |
| --- | --- | --- |
| 帳號 | `user_id` 主鍵、唯一登入名稱、密碼雜湊、`role`、`approval_status` | 帳號主責維護；角色與帳號審核狀態分開，待審帳號的權限由後端限制。 |
| 教室 | `room_id` 主鍵、唯一房號、名稱、樓層、容量、`is_bookable`、`is_schedulable` | 空間主責維護。地圖位置及全景使用同一個教室編號。建議已有歷史紀錄的空間採停用，保留舊紀錄的關聯。 |
| 借用與物品 | 申請編號、申請人、教室、起訖時間、審核狀態、審核意見；每項物品各有一筆明細 | 借用主責維護。一張申請可含多項物品，領用與歸還需能回查物品和時間。 |
| 課程與調課 | 課程編號、教師、希望教室及時段、正式排課結果；變更申請保存原時段與新時段 | 排課主責維護。週檢視讀取正式結果；老師填志願、管理員排定，以及課表確定後申請變更，是三個不同動作。 |

**每台電腦有自己的開發資料庫。** 第一次建立空資料庫，依順序套用 migrations，再載入 seed。開發中若需加欄位，例如借用要記錄歸還時間，新增一份有順序的 SQL，並在 PR 寫明套用方式。已由他人執行的 SQL 保留原內容，後續修正再加新檔。合併前用上一版資料庫驗證能保留既有資料並升級；同步後執行 `python api/manage.py init`；現有初始化程式會依序執行 migration 和 seed，SQL 須可重複執行。日常測試資料可各自增減，整合時使用同一份結構與測試資料。

## 5. 排課優先、借用審核與管理員協調

| 情況 | 系統應如何處理 |
| --- | --- |
| 教室借用資格待確認 | 仍可送出申請，由管理員依序分發。 |
| 開學第一週排課 | 一週內排定正式課表。教師填寫的希望時段與正式占用分開保存；借用週檢視依正式課表標示占用。 |
| 同教室已有正式課程 | 相同或部分重疊的時段不能再核准借用。不同教室各自判斷。建議 10:00–11:00 與 11:00–12:00 視為可銜接。 |
| 課表確定後想更動 | 提出變更申請。管理員在週曆上拖曳至新時段時，也要經過同一套衝突檢查。核定前仍顯示原正式課表。 |
| 調課撞到已核准借用 | 管理員收到通知，內容含教室、原課程、擬調時段及受影響的借用。管理員協調改期或取消後，登記處理結果，才更新正式紀錄；通知出現本身不會取消借用。 |
| 兩人同時核准或改期 | 借用與排課應在寫入時共用同一個占用檢查。建議後端在同一筆資料庫交易中鎖定受影響的教室、重查重疊、再寫入；若衝突則回報並保留原紀錄。 |

實作前由借用與排課組員確認單次日期、每週重複、學期起訖的表示方式。交叉核對至少包括同教室撞期、不同教室同時段、相鄰時段、調課待協調時仍能查到原借用四種情況。

## 6. 本機設定與帳密

| 檔案 | 內容 | GitHub 處理方式 |
| --- | --- | --- |
| `.env.example` | 提供 FastAPI 連接 PostgreSQL 所用的 `DATABASE_URL` 範例。 | 隨專案提交，讓組員知道要填什麼。 |
| `.env` | 每人在自己電腦從範本複製，填自己的實際設定。 | 只留本機。用網頁上傳時逐項確認檔案清單。 |
| `.gitignore` | 列出 `.env`、Python 虛擬環境及快取等應忽略項目。 | 隨專案提交。本機 Git 會使用此檔；網頁上傳仍由上傳者核對選取項目。 |

`localhost` 指執行程式的那台電腦。三人各自開發時，瀏覽器連本機 FastAPI，FastAPI 再連本機 PostgreSQL。整合時在同一台電腦載入整合資料，三個模組透過同一個 API 存取。起始設定及資料庫更新方式由修改者同步寫入 README。

## 7. 先完成操作，再統一做 CSS

開發期間先用基本 HTML 寫清楚表單欄位、操作按鈕、送出結果及錯誤訊息。拖曳排課、點選樓層位置、瀏覽 360° 全景屬於功能，先以簡單版確認操作是否正確。等主要功能完成，三人再共同決定配色、字型、間距與共用樣式，集中維護在網站的公開資源目錄。

## 8. GitHub 網頁版協作流程

1. **選對分支。** 在儲存庫 Code 頁點分支選單，選第 1 節列出的功能分支，確認名稱後再選 Add file → Upload files。三人各用自己的 GitHub 帳號。
2. **提交一項能說清楚的修改。** 例如「新增借用申請與物品明細」。確認檔案、目標分支和提交說明。只選這次需要的檔案，避免夾帶本機設定或整份資料庫。
3. **開 PR。** 在 Pull requests → New pull request 選 `base: main`、`compare: 自己的功能分支`。寫明改了什麼、組員如何驗證、要不要套用 SQL，以及哪些共用欄位或 API 有變動。
4. **找對人檢查。** 一般功能請另一位組員看過；若改教室清單回傳格式，優先請會用到清單的借用或排課組員確認。可直接在 PR 留言、修正同一分支後再確認。
5. **合併後同步。** 檢查完成再合併到 main。繼續使用既有功能分支時，把最新 main 合入該分支。網頁版可另開同步 PR，這時方向相反：base 選要更新的功能分支，compare 選 main。檢查差異後合併，再於本機套用需要的 SQL。
6. **共用文件另開文件分支。** 例如本規範使用 `docs/team-guidelines`，討論完成再合併到 main。組員審閱是團隊約定。
